# 固定仓库历史与跨工作区导入需求规格

## 背景

`scmRepositoryFilter.pinnedRepositories` 当前写入 VS Code 工作区配置。用户在一个项目中固定过的仓库，在打开结构相似的新项目后不会出现，只能再次手动输入路径。需要增加跨工作区的全局历史，让用户能查看以前添加过的仓库路径，并快速复用到当前项目。

## 范围（In Scope）

- 使用扩展 `ExtensionContext.globalState` 保存固定仓库历史，历史项为规范化的工作区相对路径。
- 扩展激活时，把当前工作区已有的 `scmRepositoryFilter.pinnedRepositories` 合并进全局历史，兼容升级前已有配置。
- 现有 Pin 命令成功添加仓库后，同步把相对路径写入全局历史。
- Changed Repositories 视图标题栏新增“历史仓库”按钮。
- 历史仓库界面列出全部历史项，支持多选部分导入当前工作区。
- 支持一键导入所有能在当前工作区匹配到的历史项。
- 支持删除单条全局历史；删除不影响当前工作区已固定的仓库。
- 已固定、唯一匹配、多个匹配、未匹配的历史项使用不同状态展示和处理。
- 批量写入当前工作区时去重，并沿用 `scmRepositoryFilter.pinnedRepositories` 的原格式。
- 同步更新 Harness 架构扩展点和用户 README 功能说明。

## 非目标（Out of Scope）

- 不复制、移动或克隆 Git 仓库文件。
- 不把全局历史自动写入所有工作区；只有用户执行导入时才修改当前配置。
- 删除历史时不执行 Unpin，也不修改任何工作区配置。
- 不保存绝对路径，不引入跨设备云同步协议，也不新增可编辑的历史名称或分组。
- 不改变现有 Pin/Unpin、扫描模式和 Git 操作逻辑。
- 不新增 Webview、自定义 HTML/CSS 或样式文件。

## 核心场景

### 场景一：旧配置自动进入历史

用户升级扩展并打开已有项目。扩展激活后读取当前 `pinnedRepositories`，将合法路径去重合并到 `globalState`，当前工作区配置保持不变。

### 场景二：选择部分历史仓库导入

用户打开新项目，点击“历史仓库”按钮。扩展完整发现当前工作区仓库，将历史路径按现有后缀规则匹配。用户勾选一个或多个可用历史项后确认，扩展把实际命中的当前工作区相对路径追加到配置并一次性更新。

### 场景三：一键全部导入

用户在历史列表中触发“一键全部添加”。唯一匹配项直接加入；已固定项和未匹配项跳过；歧义项逐项让用户选择实际仓库，取消某项只跳过该项，不取消其它导入。

### 场景四：删除历史

用户点击某条历史项的删除按钮。扩展只从 `globalState` 移除该历史路径并刷新当前历史列表。如果该仓库已在当前项目固定，当前 `pinnedRepositories` 不变。

## 验收标准

1. Pin 一个新仓库后，`globalState` 中出现规范化相对路径，重复 Pin 不产生重复历史。
2. 激活扩展时，当前配置中的合法历史项会合并到全局历史，空白和重复项被过滤。
3. `scmRepositoryFilter.manageRepositoryHistory` 同时注册在 `package.json` 与 `src/extension.ts`，并显示在 Changed Repositories 标题栏。
4. 历史列表支持多选；确认后仅把选中的匹配仓库追加到当前配置。
5. 一键全部导入时，唯一匹配项全部加入，已固定和未匹配项不写入；歧义项允许逐项消歧。
6. 删除一条历史后，该项从全局历史消失，但当前工作区固定列表保持完全不变。
7. 没有历史时显示明确提示且不扫描工作区；没有可导入项时不写配置。
8. `npm run check`、`npm run build`、`npm test` 和 `npm run harness:doctor` 均退出码 0，测试用例通过数大于 0。

## 风险与权衡

- 相对路径在结构相似的项目间最具复用性，但仅用短后缀可能出现多个匹配；沿用现有消歧机制避免错误导入。
- 完整扫描可能耗时，因此只在用户主动打开历史列表时执行，并使用 VS Code 进度提示，不在 Provider 渲染路径内执行。
- Quick Pick 的单项删除会改变列表数据；实现需保持选择状态并原地更新 items，避免误关闭列表。
- 全局历史可能含旧版本异常数据；读取时必须运行时过滤字符串、空值与重复项，不能直接强制断言类型。
