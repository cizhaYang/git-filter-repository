# 多仓库 Git 管理 VS Code 插件设计

## 1. 背景与目标

项目工作区的父目录下包含数百个普通、相互独立的 Git 仓库。这些仓库不是 Git Submodule，VS Code 和普通 Git 命令缺少一个清晰的统一视图来回答：

- 哪些仓库存在代码改动；
- 每个仓库改动了哪些文件；
- 文件的具体代码差异是什么；
- 如何安全地对单个仓库执行暂存、提交、拉取和推送。

插件提供独立的 VS Code 活动栏入口，递归发现当前工作区任意层级的 Git 仓库，聚合展示仓库状态，并复用系统 Git 和 VS Code 原生 Diff 编辑器完成 Git 管理操作。

首版以“数百仓库下仍保持 VS Code 响应”和“写操作绝不串仓”为核心成功标准。

## 2. 首版范围

### 2.1 包含能力

- 自动递归扫描当前 VS Code 打开的所有工作区目录；
- 识别 `.git` 目录和 `.git` 文件形式的普通 Git 仓库；
- 展示仓库名称、路径、当前分支、上游分支、ahead/behind、变更数量和刷新状态；
- 将文件按已暂存、未暂存和冲突状态分组；
- 支持未跟踪、修改、删除、重命名和冲突文件；
- 点击文件后使用 VS Code 原生 Diff 编辑器查看差异；
- 对单个文件执行暂存或取消暂存；
- 对当前选中的单个仓库执行提交、安全拉取和推送；
- 支持 Windows、macOS 和 Linux；
- 提供扫描、刷新和 Git 命令的进度、错误与诊断输出。

### 2.2 不包含能力

- 多仓库批量 commit、pull 或 push；
- 按代码块或按行暂存；
- Git Submodule 管理；
- 分支创建、切换、删除或历史图谱；
- 插件内保存用户名、密码、SSH 密钥或 Token；
- 冲突自动解决或强制执行可能产生冲突的 Pull；
- 替代 VS Code 原生代码编辑器或自行实现 Diff 编辑器。

## 3. 技术路线

核心 Git 能力直接调用用户机器上的系统 Git CLI，VS Code API 负责扩展生命周期、活动栏、树视图、命令、文件监听、配置和原生 Diff。

不以 VS Code 内置 Git 扩展的非稳定 API 作为核心依赖，也不在首版引入 `simple-git`。这样可以保持 Git 行为与用户终端一致，减少第三方封装，并覆盖标准 Git 支持的平台。

所有 Git 命令通过 Node.js `child_process.spawn` 以参数数组启动，不拼接 Shell 命令字符串，以兼容带空格路径并避免命令注入。命令固定工作目录为目标仓库根目录。

## 4. 总体架构

插件划分为以下职责单一的组件：

### 4.1 WorkspaceRepositoryScanner

负责从所有工作区根目录递归发现仓库。扫描支持取消、最大深度、排除目录和符号链接策略，不读取仓库内部 `.git` 内容。

发现 `.git` 目录或 `.git` 文件后，将其父目录记录为仓库根目录。扫描器不进入 `.git` 元数据目录，但会继续遍历该仓库的普通工作树子目录，以发现任意深度的独立嵌套仓库；这是“外层目录或仓库下存在多个普通仓库”场景的必要行为。排除规则、最大深度、目录去重和符号链接策略共同控制扫描成本并防止循环。

### 4.2 RepositoryIndex

维护规范化仓库路径到仓库状态的内存索引，负责去重、路径归属判断、排序和增量更新。多根工作区指向同一仓库时只展示一次。

索引中的状态包含：

- 仓库 ID、展示名称、绝对路径和所属工作区；
- 当前 HEAD、分支、上游和 detached HEAD 状态；
- ahead/behind；
- staged、unstaged、untracked、conflicted 文件列表；
- `clean`、`changed`、`conflicted`、`refreshing`、`error` 状态；
- 最近刷新时间和最近错误摘要。

### 4.3 GitClient

封装允许执行的 Git 子命令，并将结构化结果返回上层。仓库状态优先使用 `git status --porcelain=v2 --branch -z`，避免依赖本地化的人类可读文本。

GitClient 不直接更新界面，也不保存凭据。标准输出、标准错误、退出码、超时和取消结果均被明确区分。

### 4.4 RepositoryTaskScheduler

控制 Git 进程数量和操作顺序：

- 多仓库只读状态刷新进入全局有限并发池；
- 同一仓库的写操作严格串行；
- 写操作执行期间，暂停该仓库的自动刷新并合并重复刷新请求；
- 不同仓库的只读任务可以并发，但首版不提供同时触发多个仓库写操作的 UI；
- 扩展停用时取消可取消的扫描和只读任务，不强制终止已经进入关键阶段的写操作。

### 4.5 RepositoryTreeProvider

提供独立活动栏中的仓库总览树。树视图只消费 RepositoryIndex 的状态，不自行运行 Git 命令。

### 4.6 DiffContentProvider

为 VS Code 原生 Diff 提供 Git 侧内容：

- 未暂存修改：索引版本对比工作区文件；
- 已暂存修改：HEAD 版本对比索引版本；
- 未跟踪文件：空内容对比工作区文件；
- 删除文件：原版本对比空内容；
- 重命名文件：原路径版本对比新路径版本；
- 二进制文件：不尝试文本 Diff，展示明确提示并允许使用系统方式打开。

虚拟文档 URI 必须包含仓库 ID、文件路径、对比来源和状态版本，防止不同仓库的同名文件发生缓存串用。

### 4.7 OperationController

负责暂存、取消暂存、提交、安全拉取和推送的前置校验、确认、执行及结果刷新。所有入口都携带不可变的仓库 ID，并在执行前再次解析仓库路径，避免用户切换选中项后误操作其他仓库。

### 4.8 RepositoryDetailsView

使用 VS Code `WebviewView` 承载选中仓库的详情、提交消息输入框和操作按钮。Webview 只负责展示和发送受限消息，不直接访问文件系统或启动命令；扩展宿主对消息类型、仓库 ID、字段长度和当前仓库状态重新校验后，才调用 OperationController。

Webview 使用严格的 Content Security Policy，不加载远程脚本，不启用任意命令 URI，也不把 Git 凭据或完整命令环境传入页面。仓库树仍使用原生 TreeView，代码差异仍使用原生 Diff 编辑器。

## 5. 仓库发现与性能策略

### 5.1 首次扫描

扩展激活后显示已有缓存结果，同时在后台扫描当前工作区。首次没有缓存时显示扫描进度，但不阻塞其他 VS Code 功能。

默认排除：

- `.git`；
- `node_modules`；
- `dist`、`build`、`out`、`coverage`；
- 用户配置的 glob 或目录名。

默认不跟随目录符号链接，避免循环和扫描到工作区外。用户可通过配置覆盖最大扫描深度、排除项和符号链接策略。

### 5.2 缓存

仓库路径索引按工作区标识存入 VS Code workspaceState。缓存只用于加快启动展示，激活后必须后台验证路径是否仍存在、是否仍为 Git 仓库，并移除失效记录。

缓存不保存文件 Diff、凭据或 Git 输出中的敏感内容。

### 5.3 增量监听

由于数百仓库场景下对所有文件创建细粒度 watcher 成本过高，首版采用组合策略：

- 监听工作区目录变化，用于发现新增或删除的 `.git` 标记；
- 对已知仓库监听工作区文件事件并做仓库归属映射；
- 短时间内同一仓库的多个事件合并为一次状态刷新；
- Git 操作完成后立即刷新对应仓库；
- VS Code 窗口重新获得焦点时刷新近期活跃或可见仓库；
- 提供单仓库刷新和全量重新扫描命令。

状态刷新优先级依次为：正在查看的仓库、有改动的可见仓库、近期收到事件的仓库、其他仓库。默认并发数应保守，并允许用户配置。

## 6. 界面与交互

### 6.1 活动栏入口

插件提供独立的“多仓库 Git”活动栏图标，不修改或接管 VS Code 原生源代码管理视图。

### 6.2 仓库总览树

顶部提供仓库名称/路径筛选、刷新和更多操作入口，并展示已修改、干净、冲突、错误和扫描中的数量。

仓库默认排序：

1. 存在冲突；
2. 存在普通改动；
3. 执行中或刷新失败；
4. 干净仓库。

同组内按展示名称排序。用户可配置隐藏干净仓库。

展开仓库后按“合并冲突”“已暂存的更改”“更改”分组展示文件。文件节点显示 Git 状态、相对路径，并提供打开 Diff、暂存或取消暂存操作。

### 6.3 仓库详情

选中仓库后展示：

- 仓库名称和完整路径；
- 当前分支、上游、ahead/behind；
- 提交消息输入框；
- “提交已暂存文件”“安全拉取”“推送”按钮；
- 最近操作状态和诊断入口。

提交只提交暂存区内容。未暂存文件不会被隐式暂存。提交前要求非空提交消息和至少一个已暂存变更。

### 6.4 操作反馈

运行中的操作在目标仓库节点和详情区域显示进度，并禁用同仓库的重复写操作。成功后重新读取 Git 状态再显示成功；失败时展示简短原因，并提供打开专属 OutputChannel 查看脱敏诊断的入口。

## 7. Git 操作设计

### 7.1 暂存与取消暂存

- 暂存文件使用 `git add -- <path>`；
- 取消暂存依据 Git 版本和仓库是否存在 HEAD，选择语义等价且不会删除工作区内容的命令；
- 路径始终作为独立参数传入，并校验属于目标仓库；
- 操作完成后只刷新目标仓库。

### 7.2 Commit

提交前校验仓库不存在未解决冲突、提交消息非空且暂存区非空。使用系统 Git 的作者配置和 hooks，不在插件内伪造身份。

Git hook 拒绝、身份未配置或签名失败时，保留暂存区和提交消息，并展示可操作的错误提示。

### 7.3 安全 Pull

首版不直接执行 `git pull`。安全拉取是受控的 `fetch + 预检 + merge` 流程：

1. 锁定目标仓库、本地 HEAD、当前分支和配置的上游分支；
2. 如果处于 detached HEAD、没有上游、存在未提交/未暂存/未跟踪改动、存在未解决合并状态或正在执行其他写操作，则停止；
3. 执行 `git fetch` 更新远端引用。Fetch 允许下载对象并更新远端跟踪引用，但不得修改当前分支、索引或工作区文件；
4. Fetch 后再次确认当前分支和本地 HEAD 未被外部操作改变；
5. 如果本地 HEAD 是上游的祖先，使用 fast-forward-only 更新，避免产生合并提交；
6. 如果本地与上游已经分叉，使用 Git 的无工作区合并树能力对固定的两个提交执行预检；
7. 预检发现内容冲突时立即停止，不执行 merge 或 rebase。当前分支、索引和工作区保持原样，只保留 Fetch 更新的远端引用；
8. 预检无冲突时，向用户明确展示分支和提交差异，再执行普通非交互 merge；
9. 执行前再次验证 HEAD 和上游对象 ID 与预检一致。任何变化都使本次操作失效并要求重新预检；
10. Merge 命令仍可能因 hooks、文件权限、锁文件或磁盘问题失败。插件必须报告真实结果，不把“预检无内容冲突”等同于“最终操作必然成功”。

无工作区合并预检优先使用受支持 Git 版本的 `git merge-tree --write-tree`，通过退出码和结构化输出识别冲突。扩展激活时检测 Git 版本和该能力。如果无法可靠预检，安全拉取按钮保持不可用并提示升级 Git，不降级为普通 `git pull`，也不通过临时修改用户索引或工作区来试合并。

首版安全拉取不支持 rebase 模式。这样可确保预检算法与实际更新策略一致，避免“merge 预检通过但 rebase 仍冲突”的错误承诺。

### 7.4 Push

推送前校验当前分支和上游信息。已有上游时执行普通 push；没有上游时必须展示将要设置的远端和分支，并经用户确认后执行设置上游的 push。

插件复用系统 Git 凭据配置。认证失败时不收集或保存密码、Token 或 SSH 密钥，只提供错误摘要和在终端完成认证/配置的指引。

## 8. 错误与边界处理

- Git 不存在：禁用 Git 操作，展示 Git 路径配置和诊断入口；
- Git 版本不满足安全拉取：其他能力可用，但禁用安全拉取；
- 仓库在操作前被移动或删除：取消操作并从索引移除；
- Git 锁文件或另一个 Git 进程占用仓库：停止并提示，不自动删除锁文件；
- 命令超时：只读命令可以取消；写命令避免在不确定阶段强杀，先提示用户检查仓库状态；
- 合并冲突状态：显著标记冲突文件，允许查看，不提供可能扩大冲突的安全拉取；
- 大型或二进制 Diff：限制读取大小并展示降级提示，避免扩展宿主内存暴涨；
- 路径大小写与分隔符：使用 `vscode.Uri`、Node path API 和平台感知的规范化策略；
- 多根工作区与嵌套路径：采用最长仓库根路径匹配文件归属，确保嵌套仓库文件不会错误刷新外层仓库。

## 9. 配置项

首版提供以下配置，均有保守默认值：

- 最大扫描深度；
- 扫描排除目录或 glob；
- 是否跟随目录符号链接；
- Git 状态查询最大并发数；
- 文件事件刷新延迟；
- 是否隐藏干净仓库；
- Git 可执行文件路径；
- 单个 Git 只读命令超时时间；
- Diff 最大文本大小。

改变扫描相关配置后提示并执行可取消的全量重新扫描。改变展示配置只刷新视图。

## 10. 测试策略

### 10.1 单元测试

- porcelain v2 `-z` 状态解析，包括空格、中文和特殊字符路径；
- staged、unstaged、untracked、rename、delete、conflict 状态映射；
- 仓库去重、最长根路径归属和跨平台路径规范化；
- 排除规则、最大深度和符号链接循环防护；
- 刷新去抖、优先级、并发池和单仓库写操作队列；
- Git 错误、超时和取消结果分类；
- Diff 虚拟 URI 在多仓库同名文件场景下的唯一性。

### 10.2 Git 集成测试

使用临时目录创建真实 Git 仓库，验证：

- 单层、深层、嵌套和 `.git` 文件形式仓库的发现；
- 修改、暂存、取消暂存、提交和各种 Diff 来源；
- Fetch 不修改当前分支、索引和工作区；
- 可 fast-forward 时安全拉取成功；
- 分叉但无冲突时预检和 merge 成功；
- 分叉且有冲突时预检停止，HEAD、索引和工作区对象 ID/内容在操作前后保持一致；
- Fetch 后 HEAD 被外部改变时拒绝继续；
- push、认证失败、hooks 拒绝和 Git 锁占用的错误反馈。

### 10.3 VS Code 扩展测试

- 扩展激活、命令注册和活动栏视图加载；
- 仓库树刷新、筛选、排序和隐藏干净仓库；
- 文件节点命令携带正确仓库 ID；
- 点击不同状态文件打开正确的原生 Diff；
- 配置变化触发正确级别的刷新或重扫；
- 操作进度、按钮禁用、成功与失败通知。

### 10.4 性能测试

生成包含数百个小型仓库和大量普通目录的工作区，验证：

- 扫描可取消且扩展宿主保持响应；
- Git 状态进程数不超过配置并发；
- 高频文件事件被合并而不是触发命令风暴；
- 仓库树增量刷新，不因单仓库变化重建全部节点；
- 启动缓存能快速展示，并在后台正确淘汰失效仓库。

## 11. 验收标准

- 打开包含数百个独立仓库的工作区后，插件能逐步发现并展示仓库，不冻结 VS Code；
- 用户可以快速筛出有改动的仓库并看到具体文件；
- 点击文件能根据暂存状态打开正确的 Diff；
- 暂存、取消暂存和提交只影响明确选中的仓库与文件；
- commit 只提交暂存区内容；
- 安全拉取在预计冲突时不修改当前分支、索引或工作区；
- 所有 Git 写操作都有明确的进行中、成功或失败结果；
- 插件不持久化 Git 凭据；
- Windows、macOS 和 Linux 路径及命令参数处理一致。

## 12. 后续版本候选

在首版稳定后，再单独评估以下能力：

- 用户手动添加工作区外的扫描目录；
- 多仓库批量操作及强二次确认；
- 按代码块或按行暂存；
- 分支与提交历史可视化；
- 安全 Rebase 拉取；
- 与 VS Code 内置源代码管理视图的可选联动。
